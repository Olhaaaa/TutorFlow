# Tutorflow

Розклад і білінг для незалежних репетиторів — одне місце замість переписки в
месенджері й таблиці з балансами.

**Студент** бачить тижневий календар у власному часовому поясі, сам бронює
вільну годину й сам скасовує заняття. Якщо на балансі є кошти, заняття
оплачується одразу; якщо ні — місце закріплюється за ним і лишається
заплатити до визначеного строку. Поповнити баланс можна карткою.

**Викладач** веде тижневий шаблон доступності й розгортає його у заняття на
кілька тижнів уперед, закріплює за студентами постійні години, бачить свій
розклад з іменами, скасовує заняття з поверненням коштів і поповнює баланси
вручну.

**Гроші** рахуються в копійках і живуть у журналі транзакцій: баланс — це
сума проводок, а не окреме число, яке можна непомітно зіпсувати. Оплата
карткою йде напряму на рахунок викладача — платформа коштів не тримає й не
перераховує.

## Стек

| Шар | Засіб | Чому саме так |
|---|---|---|
| Домен | TypeScript, нуль залежностей | `packages/core` не імпортує ні Nest, ні Kysely — той самий код працює і в моноліті, і в мікросервісах |
| API | NestJS на Fastify | модуль → сервіс → репозиторій із явними межами; Fastify ще й віддає сире тіло запросу, без якого не перевірити підпис вебхука |
| Доступ до даних | Kysely | явний SQL без декораторів у домені |
| База | PostgreSQL 17 | діапазони та exclusion constraint, `UPDATE … RETURNING`, `TIMESTAMPTZ`, `JSONB` |
| Клієнт | React 19, Vite, Tailwind v4, shadcn/ui | одна мова на всіх шарах |

## Що потрібно

- Node.js ≥ 22 (використовується `process.loadEnvFile`)
- pnpm 12 (`corepack enable pnpm`)
- Docker — для локального PostgreSQL

## Запуск за пʼять команд

```bash
pnpm install
cp .env.example .env                      # значень за замовчуванням достатньо
docker compose -f compose.dev.yml up -d   # PostgreSQL 17 на :5432
pnpm --filter api migrate                 # схема
pnpm --filter api seed                    # демо-дані
```

Далі два процеси в сусідніх терміналах:

```bash
pnpm api:dev    # http://localhost:8080, Swagger на /api/docs
pnpm web:dev    # http://localhost:5173
```

Змінні оточення експортувати вручну не треба: `.env` із кореня читає сам Node.

## Тести

```bash
pnpm test
```

- `packages/core` — правила розкладу й білінгу, без бази;
- `packages/contracts` — ключ дедуплікації й текст нагадування: чисті функції,
  тому перевіряються раніше, ніж підніметься будь-яка інфраструктура;
- `services/api` — інтеграційні, **проти справжнього PostgreSQL**: атомарне
  захоплення слота, перехід на зимовий час, звірка балансу з журналом,
  ідемпотентність платіжного вебхука, одноразовість повернення при скасуванні
  викладачем, доставка завдань з `outbox` із компенсацією, ідемпотентність
  руху коштів за ключем операції;
- межі сервісів лаби 3 — **без бази**: таблиця маршрутів gateway і різ схеми
  по службах перевіряються як дані, а не прогоном компоузу на 13 контейнерів.

Інтеграційні тести працюють на тій самій локальній базі й **чистять таблиці**.
Після них демо-дані треба залити наново: `pnpm --filter api seed`.

## Розгортання на Render

Сервіс описаний у `render.yaml` — він відтворюється з файлу, а не з кліків у
панелі. Образ той самий, що перевіряється локально.

1. **База.** Створити проєкт у Neon (регіон `eu-central-1`, поруч із
   Франкфуртом) і взяти **пуловий** рядок підключення — хост із `-pooler`.
2. **Сервіс.** У Render: Blueprint → репозиторій → він читає `render.yaml`.
   Єдине, що запитає, — `DATABASE_URL`: вставити рядок із Neon.
   `JWT_SECRET` і `PAYMENT_TOKEN_KEY` платформа згенерує сама.
3. **Схема й демо-дані** — із локальної машини проти бази Neon:

   ```bash
   DATABASE_URL='postgres://…-pooler…/tutorflow?sslmode=require' pnpm --filter api migrate
   DATABASE_URL='postgres://…-pooler…/tutorflow?sslmode=require' pnpm --filter api seed
   ```

   Міграції навмисно не їдуть при старті застосунку: кілька екземплярів
   почали б мігрувати навперебій.
4. **Токен еквайрингу — ТІЛЬКИ ПІСЛЯ сідера.** `seed` чистить таблиці, а
   разом із `teachers` зникає й підключений токен. Порядок: сідер → увійти
   викладачем у розгорнутому застосунку → вкладка «Оплата» → вставити токен.

Адресу вебхука задавати не треба: Render кладе в оточення
`RENDER_EXTERNAL_URL`, і `config.ts` бере адресу звідти. Тому вже з першого
деплою вкладка «Оплата» показує справжній колбек
`https://…onrender.com/api/payments/monobank/callback`, і результат оплати
приходить вебхуком, а не добором статусу.

**Переходи станів у розгортанні з одним процесом.** Безкоштовний тариф дає
веб-сервіс і не дає фонового воркера, тому на Render прохід робить сам процес
API — за прапорцем `MAINTENANCE_IN_API=true` у `render.yaml`. У компоузі лаби 2
прапорця немає: там є воркер, і робити прохід удвох немає за чим. Обидва режими
безпечні одночасно, бо всі переходи ідемпотентні.

Чого на безкоштовному тарифі **немає**: Redis і воркера, тому шина подій
вимкнена — нагадування не публікуються й у Telegram не йдуть. Це та сама
відмінність між лабою 1 і лабою 2, тільки з боку розгортання.

Дві властивості безкоштовного тарифу, які видно одразу: сервіс засинає після
15 хвилин простою — перший запрос після сну чекає холодного старту, і разом із
процесом засинає таймер періодичних переходів (той самий привід винести їх у
воркер, що й scale-to-zero). Вебхук, який прийшов у сплячий сервіс, будить
його сам, а провайдер повторює доставку, доки не отримає 2xx.

## Лаба 2: процеси замість одного процесу

Код той самий, змінилось те, ХТО що виконує. У лабі 1 один процес віддавав
API, віддавав SPA і сам, за таймером, застосовував переходи станів. Тепер
переходи забрав окремий процес.

| Контейнер | Що робить |
|---|---|
| `postgres` | база замість керованого Neon; порт назовні не публікується |
| `redis` | шина подій між процесами — Redis Stream `tutorflow.events` |
| `migrate` | одноразовий: накладає схему й завершується; api й worker чекають саме успішного завершення |
| `api` | HTTP і SPA. **Таймера більше не має**, зате публікує події |
| `worker` | `src/worker.ts`: прохід переходів станів за розкладом **і** споживач подій |

Образ один на `api` і `worker` — той самий кореневий `Dockerfile`, що й у
розгортанні; відрізняється лише команда. Воркер піднімається через
`NestFactory.createApplicationContext`, тому не слухає порт і не має маршрутів,
але має ті самі доменні модулі й те саме впорскування залежностей. Завдяки
цьому в лабі 3, коли модулі роз'їдуться по сервісах, воркер роз'їдеться разом
із ними, а не доведеться писати його заново.

```bash
docker compose -f lab2-compose/compose.yml up -d --build
docker compose -f lab2-compose/compose.yml --profile seed run --rm seed   # демо-дані
docker compose -f lab2-compose/compose.yml logs -f worker
docker compose -f lab2-compose/compose.yml down          # -v щоб знести й базу
```

Порт API береться з `API_PORT` (типово 8080), інтервал проходу — з
`MAINTENANCE_INTERVAL_SEC` (типово 60 с). Нуль означає «один прохід і вийти» —
у такому вигляді воркер придатний для CronJob, де розкладом керує платформа.

Що саме тут варто перевірити й показати у звіті: спинити воркер, зробити
закріплення протермінованим і переконатись, що воно **лишилось**
`pre_booked` — отже переходи справді пішли з API; потім підняти воркер і
побачити в логах `звільнено закріплень: 1`. Кнопка «оновити стани» в кабінеті
викладача працює й без воркера, бо викликає той самий `runOnce`.

### Шина подій

У воркері дві роботи, і вони різні за природою. Переходи станів тягне **час** —
тому цикл з інтервалом. Нагадування тягне **подія** — тому споживач висить на
блокуючому `XREADGROUP` і нічого не опитує.

Подія — це факт, який уже зафіксований у базі: публікується ПІСЛЯ коміту й
лише тією спробою, яка справді змінила дані. Доставка at-least-once (`XACK`
стоїть після запису), а від повтору захищає унікальний `notifications.dedup_key`
у базі, а не перевірка в коді: двом паралельним споживачам перевірка не
допомогла б. Чому саме Streams, а не pub/sub чи `LISTEN`/`NOTIFY` — у
[ADR-0009](docs/adr/0009-event-bus.md).

Перший споживач закриває діру, яку видно з лабораторної 1: студент дізнавався
про скасування заняття, лише відкривши сітку. Тепер скасування народжує
нагадування в журналі `notifications`.

Без `REDIS_URL` шина вимкнена, і застосунок працює як у лабораторній 1 — події
просто не публікуються.

### Нагадування в Telegram

Канал вибирається не налаштуванням, а станом студента: є привʼязаний чат — іде
в Telegram, немає — лишається в лозі, і саме `log` пишеться в `channel`.
Доставка через **long polling**, тому публічна адреса не потрібна: бот працює
й з локальної машини. Деталі вибору — у [ADR-0010](docs/adr/0010-telegram-channel.md).

Щоб підняти канал:

1. Створити бота в [@BotFather](https://t.me/BotFather) — `/newbot`, і він
   віддасть токен.
2. Токен у `.env` (локально) або в оточення сервісу: `TELEGRAM_BOT_TOKEN=…`.
   Без нього все працює, канал просто вимкнений.
3. Студент відкриває картку «Нагадування» → «Відкрити бота». Код привʼязки
   їде в посиланні `t.me/<бот>?start=<код>`, тому набирати нічого не треба.
   Код **одноразовий**: UPDATE обнуляє його при першій привʼязці.

Бот навмисно вміє одне — звʼязати чат. Бронювати з чату ми не даємо: календар
двовимірний, а чат — ні.

Недоставлені нагадування (канал був, але не відповів) перепробує наступний
прохід воркера — у лозі це `дослано нагадувань: N`. Нагадування студентові без
привʼязаного чату перепробовувати нема за чим, тому воно одразу остаточне з
каналом `log`.

### Нагадування, які народжує час

Прохід воркера не лише застосовує переходи станів, а й публікує події про те,
що **скоро настане**: `lesson.upcoming` за добу до заняття й `payment.due` за
добу до того, як спливе строк оплати закріплення.

Памʼяті про те, кому вже нагадано, у розкладі немає навмисно — це факт журналу
нагадувань, а не властивість слота. Замість памʼяті — вікно
`[now + 24h − запас, now + 24h]`, де запас удвічі більший за інтервал проходу:
воркер, який лежав десять хвилин, однаково знайде заняття, що вийшло з точки
«рівно доба». Та сама подія через це публікується кілька разів поспіль, і це
нормально — від другого нагадування захищає `notifications.dedup_key`.
Продюсер at-least-once, споживач ідемпотентний; деталі — у
[ADR-0012](docs/adr/0012-reminders-window.md).

```
[Reminders] нагадувань про заняття: 1, про оплату: 1
[Delivery] студенту 2: Нагадування: заняття завтра.
[Notifications] lesson.upcoming: повторна доставка, нагадування вже є   ← наступний прохід
```

## Лаба 3: замір перед поділом

Перед тим як ділити моноліт на сервіси, знято базову точку — інакше після
поділу не буде з чим порівнювати. Сценарії в `lab3-k6/`, запускаються в
контейнері, нічого встановлювати не треба.

```bash
# свіжі демо-дані: сценарій бронювання витрачає слоти
docker compose -f lab2-compose/compose.yml --profile seed run --rm seed

docker run --rm -i --network host -v "$PWD/lab3-k6":/s grafana/k6 \
  run /s/contention.js -e BASE=http://localhost:8081
docker run --rm -i --network host -v "$PWD/lab3-k6":/s grafana/k6 \
  run /s/load.js -e BASE=http://localhost:8081
```

**`contention.js` — про коректність, а не про швидкість.** 60 одночасних спроб
забронювати один слот; умова проходження `bookings_won == 1`. Систему, яка
продала ту саму годину двічі, порівнювати за продуктивністю немає сенсу.

**`load.js` — критичний шлях.** 40 читань календаря і 5 бронювань на секунду
протягом 30 секунд; баланс студентів поповнюється в `setup`, щоб бронювання
йшло повним шляхом «слот плюс гроші», а не лишало слот неоплаченим.

Базова точка на моноліті (пʼять контейнерів лаби 2, одна машина):

| | p(95) | avg |
|---|---|---|
| `calendar_read` | 8.2 мс | 4.9 мс |
| `booking_write` | 14.4 мс | 9.4 мс |

1352 ітерації за 30 с, 45 запросів/с, **нуль помилок і нуль конфліктів**;
`contention.js` — рівно одне бронювання з шістдесяти спроб. Методика й
відкинуті альтернативи — [ADR-0015](docs/adr/0015-load-baseline.md).

Абсолютні числа мають сенс лише для порівняння з наступним заміром на тій
самій машині: у затримку входить усе, включно з самим k6.

## Лаба 3: пʼять сервісів замість одного процесу

Код домену той самий. Розʼїхалось те, ХТО його виконує і де лежать його дані:
кожна вертикаль отримала власний процес і власну базу, а спілкуються вони лише
по HTTP.

| Сервіс | Свої дані | Що робить |
|---|---|---|
| `identity` | реквізити входу обох ролей | пароль, токен, часовий пояс |
| `scheduling` | `teachers`, `availability_rules`, `enrollments`, `slots`, `external_busy` | доступність, бронювання, перенесення, стрічки `.ics` |
| `billing` | `students`, `transactions`, `payments`, еквайринг | баланс, журнал проводок, оплата карткою |
| `notifications` | `notifications` + проєкція контактів | журнал нагадувань, канал доставки, привʼязка чату |
| `gateway` | нічого | єдиний вхід: `/api` за префіксом і та сама SPA |

Плюс три воркери (фонова робота кожного сервіса, де вона є), чотири
одноразові контейнери міграцій, чотири Postgres і Redis. Разом 13 запущених
контейнерів проти 4 у лабораторній 2.

```bash
docker compose -f lab3-microservices/compose.yml up -d --build
docker compose -f lab3-microservices/compose.yml --profile seed run --rm reset
curl -s localhost:8083/healthz        # gateway віддає таблицю маршрутів
docker compose -f lab3-microservices/compose.yml logs -f scheduling-worker
docker compose -f lab3-microservices/compose.yml down -v
```

Назовні опублікований ЛИШЕ gateway, на `:8083`. Решта сервісів і всі чотири
бази доступні тільки всередині мережі компоузу.

### Образ один, команд вісім

Той самий кореневий `Dockerfile`, що в лабораторній 2; сервіс вибирається
аргументом: `node services/api/dist/lab3/main.js scheduling`. Доменний код не
копіювався — у кожному сервісі зібрані ТІ САМІ провайдери й контролери, що в
моноліті. Уся різниця між архітектурами лежить у пʼяти оголошеннях модулів
(`services/api/src/lab3/services.ts`) і в реалізаціях шести портів. Чому саме
так — [ADR-0016](docs/adr/0016-service-split.md).

### Схема одна, різана по межі

Кожна база отримує ПОВНИЙ набір спільних міграцій, а потім з неї прибирається
все, що цьому сервісу не належить: таблиці сусідів — `drop table … cascade`,
колонки з іншим господарем — `drop column`. Правило розподілу: у кожної
колонки один господар.

```
teachers.email, password_hash                → вхід
teachers.timezone, *_hours, calendar_token   → розклад
teachers.payment_*                           → білінг
students.email, password_hash                → вхід
students.balance_minor, calendar_token       → білінг
students.telegram_*                          → нагадування
students.name, timezone                      → копія в кожного, хто показує людину
```

Різ справжній, а не декларативний: у базі нагадувань від рядка студента
лишилось три колонки, і пошти з балансом там немає ФІЗИЧНО. Через це випадкове
звернення за межу падає з помилкою бази, а не повертає тихо застарілий рядок.
Опис різу — даними в `src/lab3/cut.ts`, перевіряється тестом. Ціна дубля імені
й зони — [ADR-0019](docs/adr/0019-profile-across-databases.md).

### Бронювання без спільної транзакції

Головна різниця архітектур. У моноліті захоплення слота й списання коштів —
одна транзакція бази, тому стан «слот заброньований, а гроші не списані»
неможливий за побудовою. Тут слот живе в базі розкладу, кошти — в базі білінгу,
і спільної транзакції не існує.

Транзакція розкладу тому пише не гроші, а **завдання** на гроші — рядок у
таблиці `outbox` ВЛАСНОЇ бази. Або є і слот, і завдання, або немає нічого.
Доставляє його той самий процес одразу після коміту; те, що не доїхало,
підбирає воркер із витримкою. Від повторного застосування захищає ключ
операції на боці білінгу.

```
scheduling: UPDATE slots … WHERE status='free'   ─┐ одна транзакція
            INSERT INTO outbox (billing.charge)  ─┘
            flush() ─── POST /internal/transfers/charge ──→ billing
                                                            INSERT transactions (op_id)
```

У моноліті той самий рядок `flush()` НЕ РОБИТЬ НІЧОГО — і це найточніше місце,
у якому видно різницю між архітектурами. Подробиці —
[ADR-0017](docs/adr/0017-booking-saga.md), ідемпотентність —
[ADR-0018](docs/adr/0018-operation-idempotency.md).

### Компенсація: що робити, коли сусід відмовив

Перевірка «чи вистачає коштів» більше не атомарна із захопленням слота. Між нею
й списанням паралельна операція встигає зрушити баланс — і тоді білінг
відповідає 409, а розклад повертає заняття в `pre_booked` зі строком оплати.

Відтворюється за дві команди: поповнити баланс рівно на одне заняття й
забронювати два слоти одночасно.

```
scheduling  WARN [SchedulingOutbox] списання за заняття 65 відмовлено
                 (не вистачає коштів): сервіс billing відмовив (409)
scheduling  WARN [Outbox] завдання 5 (billing.charge): відмова, компенсую
scheduling  LOG  [SchedulingOutbox] заняття 65 повернуто в неоплачене
```

Слот 60 лишився оплаченим, слот 65 став `pre_booked` зі строком оплати, баланс
нуль, борг 500 ₴. Тобто списання відбулось РІВНО одне, а місце за студентом
збереглося.

### Що вийшло в замірах

Ті самі сценарії `lab3-k6/`, та сама машина, обидва прогони назад-у-назад;
перед кожним — свіжі демо-дані.

| | моноліт p(95) | мікросервіси p(95) | моноліт avg | мікросервіси avg |
|---|---|---|---|---|
| `calendar_read` | 8,8 мс | 11,4 мс | 6,1 мс | 8,5 мс |
| `booking_write` | 16,8 мс | 35,7 мс | 12,0 мс | 26,8 мс |

1351 і 1352 ітерації за 30 с, 45 запросів/с, **нуль помилок і нуль конфліктів
в обох**. `contention.js` — 60 одночасних спроб забронювати один слот —
зелений в обох архітектурах: `bookings_won == 1`.

Читання подорожчало на один мережевий крок (gateway), бронювання — на три
(gateway, читання балансу, доставка списання). Памʼять: 780 МіБ проти 220 МіБ,
і більша частина різниці — чотири Postgres замість одного.

Головний результат заміру — не мілісекунди, а те, що інваріант поділ пережив:
систему, яка продала б ту саму годину двічі, порівнювати за продуктивністю не
було б сенсу.

## Доступність і зовнішній календар

Викладач зайнятий не лише заняттями. Інтервали «мене немає» лежать в
`external_busy` — саме інтервалами (`tstzrange` + GiST), бо зовнішні події не
вирівняні по нашій годинній сітці.

Усі питання «чи вільна ця година» йдуть через **один предикат**: `availableSlots`
фільтрує ним вільні слоти, календар студента ним же позначає години як `busy`.
Другого місця, де хтось порівнює час самостійно, немає — через це майбутня
синхронізація з Google Calendar буде наповненням таблиці, а не правкою
календаря. Заблокована година саме **показується** як зайнята, а не зникає зі
сітки: слот, що зник без причини, читається як поломка.

Заняття віддаються назовні стрічкою iCalendar — на неї можна підписатись у
Google Calendar чи Apple Calendar:

```
GET /api/calendar/<токен>.ics             →  text/calendar; charset=utf-8
GET /api/calendar/student/<токен>.ics     →  те саме, але заняття одного студента
```

Стрічок дві, бо й розклади різні: у викладацькій усі його заняття з іменами
студентів, у студентській — лише свої, з імʼям викладача в назві події. Токени
теж окремі (`teachers.calendar_token` і `students.calendar_token`): за самим
токеном мусить бути видно, чий розклад віддавати, а відкликати свою адресу
кожен мусить уміти, не зачіпаючи чужої.

Секрет — у самій адресі, бо календарна програма не вміє ні увійти, ні віддати
заголовок авторизації. Токен відкликається з вкладки «Доступність», і стара
адреса перестає працювати негайно (студент — зі своєї картки в кабінеті).
`UID` подій будується зі слота, тому
повторна синхронізація оновлює подію, а не створює другу; скасоване пізно
заняття віддається як `CANCELLED`, і календар прибирає його сам. Стрічка
односпрямована: Google забирає її раз на кілька годин, тому «покажи зараз» вона
не дає — [ADR-0013](docs/adr/0013-availability-and-ics.md).

### Роли воркера

У воркері три роботи, і масштабуються вони по-різному. `WORKER_ROLES` вибирає,
які з них виконує процес; порожнє значення — усі три, тобто поведінка лаби 2.

| Роль | Що робить | Як масштабується |
|---|---|---|
| `transitions` | прохід переходів станів за часом | не процес, а CronJob: `MAINTENANCE_INTERVAL_SEC=0` робить один прохід і виходить |
| `events` | споживач подій зі стріму | 0…N реплік за довжиною стріму — для цього й узята група споживачів |
| `bot` | опитування оновлень бота | **рівно 1**: Telegram розриває `getUpdates`, якщо його просять із двох процесів |

```bash
WORKER_ROLES=events docker compose -f lab2-compose/compose.yml up -d worker
#   [Worker] роли: events
```

Два рішення, які з цього випливають і вже в коді, бо потім вони коштували б
переписаної точки входу: імʼя споживача — `hostname + pid` (у контейнері pid
завжди 1, а в Kubernetes hostname дорівнює імені пода), і `XAUTOCLAIM` підбирає
повідомлення, не підтверджені понад хвилину, — бо под, убитий між читанням і
`XACK`, у лабі 4 буде штатною подією. Повний перелік наслідків —
[ADR-0011](docs/adr/0011-worker-scaling.md).

Що перевірити й показати у звіті:

```bash
# скасувати оплачене заняття в кабінеті викладача, далі:
docker compose -f lab2-compose/compose.yml logs worker | grep Notifications
#   студенту 2: Викладач скасував заняття. 500 ₴ повернуто на баланс.

# повторна доставка тієї самої події не створює другого нагадування
docker compose -f lab2-compose/compose.yml exec redis redis-cli XADD tutorflow.events '*' \
  type lesson.cancelled_by_teacher at now \
  data '{"type":"lesson.cancelled_by_teacher","slotId":104,"studentId":2,"startAt":"2026-10-13T11:00:00.000Z","refundedMinor":50000}'
#   [Notifications] lesson.cancelled_by_teacher: повторна доставка, нагадування вже є

# сигнал, за яким у лабі 4 масштабуватиметься воркер
docker compose -f lab2-compose/compose.yml exec redis redis-cli XINFO GROUPS tutorflow.events
#   pending 0, entries-read 2
```

## Скасування заняття

Правило залежить від того, ХТО скасовує, і це дві різні операції, а не одна з
прапорцем.

| Хто | Коли | Слот | Гроші |
|---|---|---|---|
| Студент | за `cancelHours` і більше до початку (межа включна) | `free` | повертаються |
| Студент | пізніше | `cancelled_late` | лишаються викладачу |
| Студент | слот був `pre_booked` | `free` | не було що списувати |
| Викладач | будь-коли до початку | `free` | повертаються **повністю** |

У викладача `cancelHours` не застосовується свідомо: це правило захищає його
час від студента, який передумав за годину до заняття, і застосувати його до
того, хто сам скасував, означало б оштрафувати потерпілого. Тому `cancelled_late`
при скасуванні викладачем не виникає ніколи, а оплачене заняття завжди
повертає кошти проводкою `refund`.

Звільнення слота й повернення — одна транзакція, і авторитетна перевірка не в
коді, а в умові `status = <прочитаний статус>` усередині `UPDATE`: студент міг
скасувати це саме заняття в ту саму мить, і без умови повернення пішло б
удвічі. Саме це перевіряє `services/api/test/teacher-cancel.test.ts` — десять
одночасних скасувань повертають кошти рівно один раз.

У кабінеті викладача скасування живе в клітинці самого заняття й робиться
двома кліками: перший показує, що саме станеться («повернути 500 ₴?»), другий
виконує.

## Перенесення заняття

Перенос — **одна** операція, а не скасування плюс бронювання: між двома
викликами місце встигають забрати, і студент лишається без заняття взагалі.

```
POST /api/slots/:id/reschedule   { "toSlotId": 126 }
```

Правило складене з наявних, а не нове: переносити можна те, що можна
**скасувати безкоштовно**, і тільки туди, куди можна **забронювати**. Межа —
`cancelHours`, інакше перенос був би безкоштовним обходом правила скасування.
Неоплачене закріплення переноситься завжди, а дедлайн оплати перераховується
від нового початку.

Оплата переїжджає разом із заняттям парою проводок — `refund` за старий слот і
`lesson_charge` за новий. Баланс не змінюється, зате за кожним заняттям видно
власне списання, а не посилання на годину, якої студент уже не відвідає.
Деталі й відкинуті варіанти — [ADR-0014](docs/adr/0014-reschedule.md).

У кабінеті студента це кнопка «перенести» на власному занятті: календар
переходить у режим вибору цілі, де вільні години пропонують «сюди», а кнопок
скасування в цей час немає — один клік мимо не повинен коштувати заняття.

## Оплата карткою

Еквайринг належить **викладачу, а не розгортанню**: кожен підключає свій
рахунок сам, у кабінеті на вкладці «Оплата», і гроші студентів надходять прямо
йому. Платформа коштів не тримає й не перераховує.

Токен провайдера зберігається зашифрованим (AES-256-GCM) і назад не
віддається — в інтерфейсі видно лише кілька останніх символів.

Серверу потрібні дві змінні:

```
PAYMENT_TOKEN_KEY=…     # ключ шифрування токенів; без нього підключити не можна
PUBLIC_BASE_URL=…       # зовнішня адреса застосунку: куди вертати користувача
                        # й куди надсилати вебхук, якщо адреса публічна
```

Є ще `MONOBANK_TOKEN` — **запасний спільний токен розгортання**. Він зручний
для одноосібної установки й для демонстрації, але на платформі з багатьма
викладачами його краще не задавати: доки викладач не підключив власний рахунок,
оплати йтимуть власнику цього токена. Інтерфейс про це попереджає прямо.

Якщо викладач оплату не підключив, студент бачить пояснення замість кнопки, а
баланс поповнює викладач вручну.

### Який саме еквайринг

Інтернет-еквайринг **monobank, «Plata by mono»**: сервер створює рахунок
(`/api/merchant/invoice/create`), студент платить на сторінці банку, результат
приходить вебхуком, підписаним ECDSA над SHA-256 (ключ — NIST P-256).

Вибір саме такий із трьох причин. Картка не торкається нашого сервера — ні
номер, ні CVV, — тому PCI DSS на застосунок не поширюється. Суми в API —
копійки, тобто цілі числа, і доменний тип грошей перетинає межу без
конвертації. А ще рахунок приймає `reference`, тому наш `payments.id` їде
разом із платежем і звіряється вручну, навіть якщо відповідь провайдера
загубилась у дорозі.

### Як перевірити оплату

Три рівні, від найдешевшого.

**1. Без провайдера взагалі.** Не задавайте `MONOBANK_TOKEN` і не підключайте
рахунок: платіжні маршрути віддають 409, студент бачить пояснення замість
кнопки — а вся грошова механіка однаково перевіряється. Викладач поповнює
баланс на вкладці «Студенти», і поповнення само закриває найближчі неоплачені
заняття. Це той самий `BillingService.credit`, який викликає й вебхук, тому
перехід `pre_booked → booked` тут справжній.

**2. Тестами.** `pnpm --filter api test` містить `payments.idempotency` —
повторний і паралельний вебхук проти справжньої бази. Підпис там свідомо не
задіяний: підробити його неможливо, а гарантія «не зарахувати двічі» живе не в
підписі, а в `UPDATE … WHERE status <> 'paid'`, тому тест заходить із рівня
сховища.

**3. Справжнім рахунком на локальній машині — без тунелю.** Потрібен лише
тестовий токен еквайрингу monobank: кабінет мерчанта на `api.monobank.ua`,
розділ еквайрингу. Справжні гроші при тестовому токені не рухаються.

```
PUBLIC_BASE_URL=http://localhost:5173    # порт Vite: /api він проксує на 8080
```

Токен викладач вставляє на вкладці «Оплата» — він перевіряється у провайдера
ДО збереження, тому неправильний видно одразу. Там же видно й долю результату
оплати: при локальній адресі вкладка прямо каже, що вебхук не замовляється.

Далі студент тисне «Оплатити», платить на сторінці банку, провайдер повертає
його на `/#payment-<id>`, і сторінка повернення опитує статус кожні дві
секунди. Вебхук сюди не прийде — і не мусить: поки платіж висить `pending`,
сервер **сам питає провайдера** про стан рахунку (`PaymentsService.reconcile`)
і зараховує кошти тим самим шляхом, що й вебхук. Тому кошти зʼявляються на
балансі, а найближчі неоплачені заняття закриваються.

Локальну адресу вебхука ми провайдеру не віддаємо навмисно: `localhost` для
нього означає його власну машину, і обіцяти адресу, куди він не дійде,
означало б ховати проблему. Правило, яка адреса годиться, живе в
`payments/urls.ts` і має власні тести.

**4. Повний шлях із вебхуком.** Потрібна адреса на https, видна з інтернету:
у хмарі це URL Cloud Run, локально — тунель.

```bash
cloudflared tunnel --url http://localhost:8080   # або: ngrok http 8080
```

Виданий тунелем https-адрес кладеться в `PUBLIC_BASE_URL`, API
перезапускається — і вкладка «Оплата» показує вже конкретну адресу колбека.
Тепер кошти зараховує вебхук, зазвичай раніше, ніж користувач повернеться у
застосунок. Добір статусу від цього не стає зайвим: вебхук губиться й у
продакшні, і тоді він лишається другою лінією.

`MONOBANK_API_BASE` підміняє адресу провайдера, тобто дозволяє підставити
власну заглушку, яка віддає `/api/merchant/pubkey` і підписує тіла своїм
ключем. Для ручної перевірки це дорожче за тунель, але в CI воно знадобиться.

> `pnpm --filter api seed` і інтеграційні тести **очищають таблиці**, а разом
> із `teachers` зникає й підключений токен еквайрингу. Після них його треба
> вставити заново.

## Структура

```
packages/core        домен: гроші, автомат станів слота, правила
packages/contracts   межа між сервісами: події, тіла внутрішніх викликів, outbox
services/api         NestJS: scheduling, billing, payments, auth, notifications
  src/outbox         журнал відкладених доставок і точка дренажу після коміту
  src/lab3           композиції пʼяти сервісів, HTTP-адаптери портів, різ схеми
apps/web             React: календар, баланс, кабінет викладача
lab2-compose         компоуз лаби 2: пʼять контейнерів, одна база
lab3-microservices   компоуз лаби 3: пʼять сервісів, чотири бази
lab3-k6              навантажувальні сценарії, однакові для обох архітектур
```

Сторінка `/#styleguide` малює всі стани заняття поруч із палітрою — це
специфікація інтерфейсу, яка не може розійтися з реалізацією, бо бере ті самі
компоненти. Посилання на неї в інтерфейсі немає: вона відкривається рівно за
цією адресою.
