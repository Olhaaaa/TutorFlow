# ADR-0016. Розгортання в Google Cloud: Terraform + GKE

Статус: прийнято
Дата: 2026-10-18
Автор: —

## Контекст

Лаба 1 жила на Render + Neon: один веб-процес, переходи станів за таймером у
ньому ж, без Redis і без воркера. Лаба 2 розклала застосунок на контейнери
(api, worker, redis, migrate), але лише в Compose на ноутбуці. Лаби 3 і 4
вимагають більшого: обидві версії (моноліт і мікросервіси) розгорнуті в хмарі
на порівнянному залізі, плюс засоби керування ресурсами — масштабування,
моніторинг, відтворюване розгортання.

Що з цього випливає для платформи:

- **Довгоживучі процеси без HTTP.** Воркер висить на `XREADGROUP`, бот — на
  long polling `getUpdates`, Redis тримає стрім. Serverless їх або присипляє,
  або бере гроші за постійно виділений CPU.
- **Лаба 4 уже спроєктована під Kubernetes** (ADR-0011): `events` — KEDA за
  довжиною стріму, `bot` — рівно одна репліка, `transitions` — CronJob.
- **Бюджет** — пробні 300 $ на 90 днів.
- **Вдвох.** Інфраструктура мусить відтворюватись з репозиторію, а не з
  кліків у консолі.

## Рішення

**Terraform описує платформу, Helm — застосунок.**

Terraform (`infra/terraform`): VPC з Cloud NAT, зональний кластер GKE Standard
з одним пулом spot-вузлів і cluster autoscaler, Cloud SQL PostgreSQL 17 з
приватною адресою, Artifact Registry, статична IP на кожне середовище, KEDA,
namespace-и й згенеровані секрети. Змінюється рідко.

Helm (`infra/helm/tutorflow`): Deployment API з HPA, воркер (режим `single` як
у Compose або `split` як в ADR-0011), Redis як StatefulSet, міграції хуком
`pre-upgrade`, Ingress з керованим сертифікатом. Змінюється з кожним комітом.

**Середовища — ключі однієї мапи.** `var.environments` = { monolith, microservices }:
спільні кластер і інстанс SQL, окремі namespace, користувач БД, бази, адреса,
секрети. Порівняння в лабі 3 — на тому самому залізі.

**Адреса відома до деплою.** Статична IP з Terraform → хост
`<ip>.sslip.io` → `PUBLIC_BASE_URL` кладеться в ConfigMap ще до першого
релізу. Сертифікат на цей хост видає Google, тож вебхук monobank отримує
https без власного домену.

## Наслідки

+ Усе відтворюється з `terraform apply` і `infra/deploy.sh`; `terraform destroy`
  прибирає рівно те, що створено, і рахунок зупиняється.
+ ADR-0011 реалізується без зміни коду: `--split` вмикає KEDA і CronJob.
+ Логи й метрики (Cloud Logging, Managed Prometheus, Query Insights) — без
  жодного агента, встановленого руками.
+ Приблизно 45–60 $/міс. (вузол spot e2-standard-2, db-f1-micro, балансувальник,
  NAT). Плату за керування зональним кластером покриває free tier GKE.
− Spot-вузол Google може забрати з попередженням за 30 с. Для демонстрації
  прийнятно; для показу на захисті — `spot = false` на день.
− Секрети живуть у стані Terraform. Локальний стан — на одному ноутбуці;
  для роботи вдвох — бакет GCS з обмеженим доступом.
− Redis у кластері, а не Memorystore: дешевше в рази, але бекапи й
  відмовостійкість — на нас (appendonly + PVC).
− Перший випуск сертифіката — до години; до того застосунок доступний по http.

## Розглянуті альтернативи

**Cloud Run + Cloud SQL** — найпростіше для API і найдешевше в простої.
Відкинуто як основну платформу: воркер, бот і Redis не є HTTP-сервісами, а
KEDA й CronJob з ADR-0011 довелося б замінювати на Cloud Run Jobs і
Cloud Scheduler — інша лаба 4, ніж та, що спроєктована.

**GKE Autopilot** — без вузлів узагалі, оплата за поди. Відкинуто: дорожчий
на постійно ввімкнених подах і обмежує DaemonSet-и та вебхуки, які потрібні
KEDA; spot-вузол Standard виходить у кілька разів дешевше.

**Memorystore для Redis** — керований, але найменший інстанс ~35 $/міс. за
буфер на кілька тисяч подій.

**Terraform для всього, включно з релізом застосунку** (`helm_release`) — одна
команда замість двох. Відкинуто: кожен деплой коду ставав би зміною
інфраструктури в стані Terraform, а мікросервіси в лабі 3 мають свій чарт.
